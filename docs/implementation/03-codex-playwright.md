# 3단계: Codex App Server로 Playwright 코드 생성

## 구현 흐름

1. `POST /api/runs/{실행ID}/generate-playwright`에 2단계 실행 ID를 전달한다.
2. API가 해당 실행의 `test-spec.json`과 로컬 화면 참고 HTML을 `generated-tests/`에 임시 입력으로 둔다.
3. Codex CLI `0.164.0`의 App Server를 자식 프로세스로 실행하고 JSONL over stdio로 연결한다.
4. `initialize`와 `initialized` 후 `thread/start`, `turn/start`를 호출한다. Codex CLI의 기존 로그인과 기본 모델을 사용한다.
5. Codex는 화면 참고 HTML과 명세를 읽고, 실제 화면 요소와 연결되는 테스트만 `generated-tests/*.spec.ts`로 저장한다.
6. 입력 자료가 바뀌지 않았는지 해시를 확인하고 임시 입력을 지운다.
7. `playwright test --list`로 생성 파일과 테스트 개수를 확인한다. 이 단계에서는 테스트를 실행하지 않는다.

## 접근 범위와 키 분리

- Codex 작업 폴더는 해당 실행의 `generated-tests/`다.
- Codex sandbox는 `workspace-write`, approval policy는 `never`로 요청한다. 추가 승인이 필요한 요청은 자동 허용하지 않는다.
- 실행 폴더 외부 파일 변경을 지시하지 않는다. 테스트 파일이 아닌 출력은 거부한다.
- API LLM의 `OPENAI_API_KEY`는 Codex 자식 프로세스 환경에서 제거한다. Codex는 로그인된 Codex CLI 인증을 사용한다.
- thread는 실행별 임시 thread로 생성한다.

## 확인 결과

- 입력 실행: `e4f5866b049a46a4a7ff6e5421389b86`
- 입력 명세: 전체 제품 요구사항 75행, 상황 176건
- 생성 파일: `.local/runs/e4f5866b049a46a4a7ff6e5421389b86/generated-tests/product-demo.spec.ts`
- Playwright 인식 결과: 테스트 11건, 파일 1개
- 생성 기록: `.local/runs/e4f5866b049a46a4a7ff6e5421389b86/generation.json`
- 테스트 실행: 하지 않음

Codex는 현재 예제 화면의 실제 컨트롤과 기대 결과를 연결할 수 있는 11개 상황을 작성했다. 나머지 165개는 예제 화면에 대응 화면이나 확인 가능한 관찰 결과가 없어 제외했고, scenario key와 사유를 `generation.json`에 기록했다. 따라서 전체 제품 요구사항을 점검할 수 있는 테스트가 완성된 것은 아니다. 4단계 실행 전에 대상 앱과 제품 기능 범위를 맞춰야 한다.

현재 명세의 대상 주소 `http://127.0.0.1:8765/product-demo.html`는 생성 당시 실행 중이지 않았다. 코드는 `examples/product-demo.html`을 화면 참고 자료로 사용했다. 실제 대상 주소는 4단계에서 준비해 연결한다.

## 호출 예시

    POST http://127.0.0.1:8000/api/runs/e4f5866b049a46a4a7ff6e5421389b86/generate-playwright

3단계 산출물은 다음 단계의 Playwright 실행 입력이다.

## 원문 한 건의 실제 변환 과정

예시는 PDF 1쪽 표 5행의 `BE_USER_001` 회원가입 요구사항이다.

### 원문과 임베딩 저장

| 처리 | 실제 값 |
| --- | --- |
| 제품 원본 | `documents/product/v1/제품_요구사항_정의서.pdf` |
| 검색용 텍스트 | `documents/product/v1/requirements.md`의 요구사항 75행. PDF 쪽과 표 행, 요구사항 ID를 같이 기록 |
| 문단/조각 | `requirements.md`, 문단 4, 조각 1 |
| 원문 길이 | 356자. 800자 기준보다 짧아서 한 조각으로 저장 |
| 임베딩 모델 | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` |
| 벡터 | 384개 실수값. 원문과 함께 SQLite `chunks.embedding`에 JSON 문자열로 저장 |

임베딩은 문장을 같은 의미 공간의 숫자 좌표로 바꾸는 인코딩이다. 같은 모델로 검색어도 벡터화하고, 저장 벡터와 코사인 유사도 `내적 / (두 벡터 길이의 곱)`를 계산해 가까운 문장을 찾는다. 벡터를 원문으로 복원하는 과정은 없고, 벡터 자체를 OpenAI API에 보내지도 않는다. API 토큰을 줄이는 효과는 임베딩 숫자를 보내서가 아니라, 검색으로 관련 원문 조각만 골라 보낼 때 생긴다.

SQLite에는 `path + paragraph_no + chunk_no`를 키로 원문과 벡터를 함께 보관한다. 별도 `source_files`에는 원본 파일의 SHA-256을 저장한다. 임베딩 후 문서가 바뀌면 기존 벡터와 원문이 어긋나므로 검색을 중단한다.

### 검색 범위에 따른 차이

- 실제 생성에 쓴 실행은 `scope=전체`다. 이 경로는 벡터 순위로 요구사항을 줄이지 않고 제품 요구사항 75행을 모두 가져온다. 전체 제품을 검사하겠다는 요청이기 때문이다.
- 자유 검색어를 넣으면 검색어도 같은 모델로 임베딩하고 원문 문구 검색과 코사인 유사도 검색을 결합한다. 별도 원리 확인 질의 `일반 회원가입 필수 입력과 이메일 인증`의 상위 결과는 이메일 인증 0.7943, 비밀번호 찾기 0.7383, 회원가입 0.7068이었다.
- 따라서 앞의 전체 실행에서 회원가입 문단이 유사도 순위로 뽑혔다고 설명하면 부정확하다. 전체 경로에서는 75행 모두 선택됐다.

### 검색 근거에서 테스트 코드까지

| 단계 | 실제 산출물 |
| --- | --- |
| 원문 근거 | `BE_USER_001@pdf:1:5`, `requirements.md` 문단 4 조각 1. 이용약관 동의, 필수 정보, 이메일 인증, 비밀번호 조건, 빈 입력 경고가 적혀 있다. |
| API 명세 | 허용: 필수 정보를 넣고 이메일 인증 완료 후 가입. 거부: 정보를 비운 채 가입 버튼을 눌러 빨간 경고를 확인. 원문 조각의 경로와 번호를 두 상황에 연결한다. |
| Codex 코드 | 테스트 이름에 `BE_USER_001@pdf:1:5-ALLOW-1`, `...-DENY-2`를 보존하고 `getByLabel`, `getByRole`, `expect`로 실제 UI를 확인한다. |
| Playwright 목록 | 생성 파일 1개에서 11개 테스트를 읽었다. 이 요구사항은 그중 2개다. |

전체 범위에서는 75행을 12행씩 묶어 총 7번 OpenAI API에 보냈다. 전송한 것은 원문 근거와 출처 정보이지 384개 숫자로 된 임베딩 벡터가 아니다. 생성 명세에는 전체 176개 상황이 있었고, Codex는 예제 화면에서 실제 컨트롤과 결과를 연결할 수 있는 11개만 코드로 만들었다.

회원가입 예제 화면의 `이메일 인증 완료`는 실제 이메일 발송이나 코드 인증이 아니라 체크박스다. 그러므로 생성된 테스트가 검증하는 것은 예제 화면의 체크 상태와 가입 결과다. 이메일 전송, 중복 확인, 데이터베이스의 비밀번호 암호화는 검증하지 않는다.

## 임베딩 모델의 원리와 이번 실행의 입력 변화

### 모델 이름 해석

`paraphrase-multilingual-MiniLM-L12-v2`는 답변을 생성하는 LLM이 아니라 문장 간 의미 유사도를 검색하는 임베딩 모델이다.

- `paraphrase`: 문장 표현이 달라도 의미가 비슷한 문장을 가까운 벡터로 놓도록 만든 목적이다.
- `multilingual`: 50개 이상 언어를 다룬다. 평행 문장, 즉 서로 번역된 문장을 의미 공간에서 가깝게 놓도록 학습됐다. 한국어 질의도 같은 모델로 벡터화해 검색한다.
- `MiniLM-L12`: 12개 Transformer 층으로 문맥을 반영한다. MiniLM은 더 큰 모델에서 문장 표현을 배우도록 압축/증류된 계열이다.
- `v2`: 이 모델 계열의 두 번째 버전이다.

실제 모델 카드는 문장/문단을 384차원 벡터로 변환한다고 설명한다. Transformer가 각 토큰의 문맥 벡터를 계산한 다음, padding을 제외한 토큰 벡터들을 평균 내 문장 벡터로 만든다. 그래서 단어가 일치하지 않아도 문맥이 비슷한 표현을 검색할 수 있다. 의미가 맞는지 판정하거나 요구사항 정책을 이해해 테스트를 만드는 기능은 없다. 그 작업은 이후 OpenAI API가 원문을 읽고 수행한다.

참고: [모델 카드](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2), [다국어 학습 설명](https://sbert.net/examples/sentence_transformer/training/multilingual/README.html), [FastEmbed 모델 목록](https://qdrant.github.io/fastembed/examples/Supported_Models/).

### 실제 실행에서 텍스트가 바뀌는 순서

| 순서 | 입력 | 처리 원리 | 실제 결과 |
| --- | --- | --- | --- |
| 0 | PDF 9쪽 | `scripts/import_product_pdf.py`가 표의 ID, 제목, 상세, 페이지, 표 행을 읽고 75행/74개 고유 ID인지 검사 | 원본 PDF는 보존하고 `requirements.md`를 생성. 임베딩 런타임은 PDF를 직접 읽지 않음 |
| 1 | Markdown | 빈 줄 기준 문단 분리, 연속 공백 정리 | `requirements.md` 문단 4에 회원가입 한 행 |
| 2 | 문단 | 800자보다 길면 공백 위치를 기준으로 조각 분리 | 이 행은 356자라 조각 1개 |
| 3 | 조각 문자열 | FastEmbed가 토큰화하고 ONNX MiniLM 12층으로 토큰 문맥을 계산, 토큰 평균 풀링 | 384개 실수값 벡터 |
| 4 | 원문+벡터 | SQLite에 원문, 벡터, 경로, 문단 번호, 조각 번호 저장 | `chunks`의 복합 키는 `(path, paragraph_no, chunk_no)` |
| 5 | 검색 질의 | 같은 모델로 질의 벡터 생성, 저장 벡터와 코사인 유사도 계산. 동시에 원문 문자열 검색 | 질의별로 가까운 요구사항 후보를 선택 |
| 6 | 근거 목록 | 임베딩 대신 선택된 원문 텍스트와 출처를 묶음 | `evidence.json` |
| 7 | OpenAI API | 원문 근거 12행씩 구조화 JSON 요청 | `test-spec.json`의 허용/거부 상황과 기대 관찰 결과 |
| 8 | Codex App Server | 명세와 예제 HTML을 읽어 접근성 라벨/버튼 등 실제 요소를 사용 | `generated-tests/*.spec.ts` |
| 9 | Playwright Test | `--list`로 테스트 코드가 로드되는지만 확인 | 이번 생성물 1파일, 11건 인식. 테스트 실행은 안 함 |

모델의 실제 입력 한도는 128토큰이다. 이전에 88조각 모두 한도 이내라고 기록한 것은 토크나이저의 자동 잘림이 켜진 상태에서 길이를 세어 잘못 확인한 결과였다. 잘림을 해제하고 다시 세면 88조각 중 27개가 한도를 넘고, 최대 336토큰이다. 회원가입 조각은 356자, 실제 178토큰이며 임베딩할 때 128토큰으로 잘린다. 따라서 뒤쪽의 빈 입력 경고 문구는 해당 벡터에 반영되지 않는다. 원문 텍스트는 SQLite에 끝까지 저장되어 전체 범위 API 입력에는 포함된다. 문자 수 기준 분할을 토큰 기준으로 수정하고 재임베딩해야 한다.

### 이 실행에서 벡터가 실제로 검색에 쓰였는가

이번 예시의 실행 요청은 `scope=전체`였다. 따라서 75개 요구사항을 모두 가져오는 경로를 탔고, 코사인 순위로 후보를 고르지 않았다. 실제 `retrieve_evidence`는 이 경로에서 SQLite의 벡터도 읽고 파싱하지만 선택에는 사용하지 않는다. 위 자유 검색어 점수는 모델 동작을 확인하려고 별도로 계산한 값이다.

범위를 자유 검색어로 주면 구현은 다음을 결합한다.

1. ID, 제목, 원문, 영역에서 검색 문구가 포함된 요구사항을 찾는다.
2. 같은 문구를 384차원 벡터로 만들고 각 요구사항의 조각 벡터와 코사인 유사도를 계산한다.
3. 의미 유사도 상위 8개와 문자열 일치 결과를 합쳐 출처와 원문을 남긴다.

`전체`, 영역 이름, 요구사항 ID를 입력하면 각각 전체 행, 해당 영역, 해당 ID로 직접 필터한다. 이 세 경로는 벡터 유사도 순위를 사용하지 않는다.

### 현재 단계 점검에서 확인된 미완성

| 확인 항목 | 현재 상태 |
| --- | --- |
| PDF의 기획 내용을 검색 문서로 변환 | PDF importer가 표 구조로 읽고 75행/74 ID 및 중복 ID를 확인한다. |
| 1/2단계 LangGraph | `retrieve_evidence → build_handoff` 두 노드다. |
| 3단계 Codex 연결 | `/api/runs/{run_id}/generate-playwright`가 별도 함수로 App Server를 호출한다. 아직 LangGraph의 `generate_playwright` 노드로 연결하지 않았다. 계획한 통합 그래프와 차이가 있다. |
| 화면에서 실행 | React 화면에는 생성 버튼이 없다. API/Swagger 경로만 있다. |
| 대상 화면 관찰 | 생성 때 `127.0.0.1:8765`가 꺼져 있었다. Codex는 실시간 브라우저가 아니라 복사된 `product-demo.html` 파일을 읽었다. |
| 전체 요구사항 코드 | 176 상황 중 예제 HTML에 직접 대응된 11개만 생성했다. 165개는 화면 기능/관찰 결과가 없어 제외됐다. |
| 실제 Playwright 실행 및 결과 분류 | 아직 안 했다. 4단계 이후 대상 서버를 준비해 실행해야 한다. |

App Server 첫 연결에서는 `runtimeWorkspaceRoots`가 CLI 0.164.0에서 `experimentalApi` capability를 요구해 `thread/start`가 실패했다. 해당 선택 옵션을 제거하고 `cwd=generated-tests`, `sandbox=workspace-write`로 다시 연결해 생성했다. 이 오류와 해결은 프로토콜 버전에 종속된 설정 차이였다. `turn/start`에는 모델을 지정하지 않았고 당시 로컬 Codex 기본 설정은 `gpt-6-luna`였다. 현재 생성 기록에는 실제 사용 모델을 별도 필드로 저장하지 않으므로 실행 감사 정보로는 부족하다.


## 회원가입 원문 한 문장을 따라간 중간점검

1. 원문: “회원가입 버튼 클릭시 미입력 정보가 있으면 입력칸 하단에 빨간색 경고 메세지 제공”.
2. 문서: PDF 1쪽 표 5행을 requirements.md의 문단 4, 조각 1로 저장한다. ID와 출처 등 앞뒤 내용을 포함한 356자 전체가 임베딩 입력이다.
3. 토큰: 실제 178토큰이지만 현재 토크나이저는 128개로 자른다. 잘린 입력은 “입력값 숨” 근처에서 끝나므로 위 경고 조건이 벡터에 반영되지 않는다.
4. 벡터: 12층 Transformer의 토큰 문맥 벡터를 평균 풀링해 384개 실수로 만든다. 저장된 앞 6개 값은 [0.023541279137134552, -0.0033408068120479584, -0.04436489939689636, -0.043631188571453094, -0.17750944197177887, 0.013511113822460175]이다.
5. SQLite: 원문 356자 전체와 앞부분으로 만들어진 벡터를 같은 행에 저장한다. 이번 전체 범위 검색은 모든 요구사항의 원문을 읽으므로 경고 조건도 API에 전달된다.
6. API 명세: 비어 있는 일반 회원가입 화면에서 회원가입 버튼 클릭 → 입력칸 아래 빨간 경고 표시 → expected_policy=deny, scenario_key=BE_USER_001@pdf:1:5-DENY-2로 저장한다.
7. Codex 코드: 화면 HTML에 맞춰 회원가입 버튼을 누르고 #member-status의 “올바른 이메일을 입력해 주세요.”와 error 클래스를 확인하는 테스트로 바뀐다. 이 코드는 원문의 입력칸 하단 위치와 실제 빨간색까지 검사하지 않는다. 원문 전체 판정 조건을 그대로 검증한 것은 아니다.
8. Playwright --list: 해당 테스트가 코드에서 발견됐다는 사실만 확인한다. 실제 클릭이나 성공/실패 결과는 아직 없다.
