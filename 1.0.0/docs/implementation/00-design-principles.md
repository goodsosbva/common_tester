# 00. Common Tester 설계 근거와 동작 원리

이 문서를 먼저 읽고 [1단계부터의 구현 기록](README.md)을 보면 된다. 여기서는 **무엇을 해결하려고 했는지**, **왜 이 구조를 골랐는지**, **실제로 어떤 순서로 동작하는지**를 설명한다. 각 단계 문서는 그 판단을 코드로 옮긴 과정이다.

## 1. 출발점과 완료 기준

- **해결할 문제:** 화면 테스트를 사람이 매번 작성하면 정책 문서에 있는 입력 규칙을 빠뜨리거나, 기대 결과의 근거를 확인하기 어렵다.
- **만들 기능:** 등록된 정책과 화면 정보를 바탕으로 테스트 계획을 만들고, 사람이 계획을 확인한 뒤 브라우저에서 실행한다.
- **확인할 결과:** 사례마다 정책 근거, 실제 통과 또는 실패, 화면 캡처를 남긴다. 실패한 사례에는 Playwright trace도 남긴다.
- **현재 대상:** 모델을 통한 생성과 승인 흐름은 등록된 데모 주문 폼인 `demo-orders`의 `/fixtures/order.html`에서 검증했다. 임의 사이트 전체를 자동 테스트하는 범용 제품으로 검증한 상태는 아니다.

전체 흐름: `대상 등록 → 정책 검색과 화면 확인 → TestPlan 생성 → 서버 검증 → 사람의 승인 → Playwright 실행 → 결과와 캡처 저장`

## 2. 핵심 설계 판단

### 계획을 먼저 데이터 형식으로 고정한다

- **근거:** 모델이 자유 문장으로 테스트를 설명하면 실행기가 어떤 요소에 무엇을 입력하고 무엇을 확인할지 안정적으로 해석할 수 없다.
- **원리:** [TestPlan](../../api/app/models.py)에 대상, 화면 요소의 locator, 조작 단계, 기대 결과, 근거 출처를 정의한다. 생성기와 실행기는 이 형식을 통해 데이터를 주고받는다.
- **검증:** Pydantic이 누락된 값, 중복 ID, 존재하지 않는 필드 참조를 거부한다. [validation.py](../../api/app/validation.py)는 실행 대상과 계획 대상, 정책 근거 ID 및 버전을 대조한다.
- **저장:** 목록 조회에 필요한 실행 ID와 상태는 PostgreSQL의 일반 열에, 사례마다 구조가 달라지는 계획은 JSONB에 둔다. 저장 전에 서버가 검증한다.

### 정책을 검색하고 출처를 계획에 남긴다

- **근거:** 모델의 기억만으로 “주문명 최대 20자” 같은 규칙을 정하면 잘못된 테스트를 만들 수 있다. 어떤 정책 버전을 근거로 삼았는지도 확인할 수 있어야 한다.
- **원리:** [policies.py](../../api/app/policies.py)가 정책을 문단으로 나누고 FastEmbed로 벡터를 만든다. 검색할 때 먼저 `project_id`와 `version`으로 범위를 좁힌 다음, 코사인 유사도와 한국어 두 글자 묶음 일치 점수를 합쳐 순위를 매긴다. 결과에는 원문을 다시 찾을 수 있는 `source_id`가 붙는다.
- **검증:** 계획이 존재하지 않는 출처나 다른 버전의 출처를 인용하면 저장을 거부한다. 자체 샘플 검색 24문항의 기대 문단 Top-1은 24/24였다. 이는 작은 평가 집합의 결과다.
- **선택 이유:** 현재 문단 수가 적고 로컬 PostgreSQL에 pgvector가 없어 벡터를 `REAL[]`로 저장한 뒤 Python에서 비교한다. 문서가 많아질 때의 검색 성능은 아직 검증하지 않았다.

### 모델에는 제한된 조회 도구만 제공한다

- **근거:** 모델이 필요한 정책과 화면 정보를 확인할 수 있어야 하지만, 파일이나 URL을 마음대로 읽거나 코드를 실행하게 할 이유는 없다.
- **원리:** [generator.py](../../api/app/generator.py)는 Responses API에 `search_policy`, `read_project_file`, `inspect_page` 세 도구만 등록한다. 첫 호출은 정책 검색으로 고정한다. 모델의 도구 이름과 JSON 인자를 서버가 검사하고, 등록된 정책 버전, 파일, 화면 경로 안에서 실행한 결과만 모델에 돌려준다. 도구 호출은 최대 8회다.
- **검증:** 최종 응답도 `TestPlan`으로 파싱하고 서버에서 다시 검증한다. 모델이 반환한 임의 Python 코드나 SQL은 실행하지 않는다. 도구 호출 기록과 모델 응답 ID는 실행에 남긴다.

### 검증과 승인 뒤에만 브라우저를 실행한다

- **근거:** 형식이 맞는 계획이라도 기대값이 정책의 뜻을 정확히 반영하는지는 자동 검증만으로 확정할 수 없다.
- **원리:** [workflow.py](../../api/app/workflow.py)의 LangGraph는 `draft → validate → review → execute → report` 순서로 이동한다. 검증이 실패하면 오류를 전달해 한 번 다시 생성한다. `review`에서 `interrupt()`로 멈추고 PostgreSQL 체크포인트에 상태를 남긴다. 승인 요청이 오면 같은 실행 ID로 재개한다.
- **검증:** 승인 전에는 실행 API가 브라우저를 시작하지 못한다. 승인하면 실행하고 거절하면 `rejected`로 끝난다. 중단 뒤 재개하는 경로를 확인했다.
- **남은 판단:** 출처 ID의 실재 여부는 자동 검사하지만, 기대값이 원문에서 논리적으로 도출되는지는 검토 화면에서 사람이 판단한다.

### 실행은 재현 가능한 브라우저 증거로 남긴다

- **근거:** “통과”라는 상태만 있으면 무엇을 입력했고 화면이 어떻게 보였는지 확인하기 어렵다.
- **원리:** [runner.py](../../api/app/runner.py)는 사례마다 새 Chromium context를 만든다. 계획의 locator가 정확히 한 요소와 일치하는지 확인한 뒤 허용된 조작과 assertion만 실행한다. 각 사례의 최종 화면을 PNG로 저장하고, 실패한 사례는 trace ZIP도 저장한다.
- **검증:** 정상 화면에서는 통과하고 의도적으로 주문명 제한을 바꾼 화면에서는 실패를 감지했다. 사례별 상태와 증거 경로는 실행 결과에 저장한다.

## 3. 기술을 이렇게 배치한 이유

| 기술 | 맡긴 역할 | 선택 근거 |
| --- | --- | --- |
| React, TypeScript | 대상 입력, 계획과 정책 원문 검토, 승인, 결과 확인 | 사람이 검토해야 하는 지점을 화면에서 명확히 보여준다. |
| FastAPI, Pydantic | 요청 처리, 도구 실행, 계획 형식 검증 | Python의 모델 호출, 정책 검색, Playwright 실행과 같은 서버 코드에서 직접 연결된다. |
| PostgreSQL | 실행 상태, 정책 버전, 계획과 결과, LangGraph 체크포인트 보관 | 승인 대기 뒤에도 실행을 조회하고 이어갈 수 있다. |
| FastEmbed | 한국어 정책 문단의 의미 기반 검색 | 외부 임베딩 API 없이 로컬에서 샘플 정책을 색인한다. |
| LangGraph | 생성, 보정, 승인 대기, 실행의 상태 전이 | 검토 지점에서 멈췄다가 같은 실행을 재개한다. |
| Playwright | 실제 브라우저 조작과 화면 증거 수집 | 계획의 단계와 기대 결과를 화면에서 확인한다. |

## 4. 왜 1단계부터 순서대로 만들었나

1. **기반:** 실행 ID와 `TestPlan` 형식, 저장 경로를 먼저 정한다. 이후 기능이 같은 형식을 사용한다.
2. **실행기:** 사람이 만든 계획을 브라우저에서 실행해 형식이 실제 동작으로 이어지는지 확인한다.
3. **정책 검색:** 계획이 참조할 정책 원문과 버전, 출처 ID를 만든다.
4. **모델 도구 호출:** 모델이 검증된 정책과 화면 자료를 조회한 뒤 계획을 생성하게 한다.
5. **워크플로:** 생성, 검증, 한 번의 보정, 사람 승인, 실행을 하나의 상태 흐름으로 묶는다.
6. **검토 화면:** 계획과 원문 근거를 사람이 읽고 승인할 수 있게 한다.
7. **품질 평가:** 검색, 계획 검증, 브라우저 실행을 각각 고정 사례로 검사한다.
8. **배포 구성:** Docker Compose 구성을 작성한다. 컨테이너 실행은 Docker Desktop 오류로 아직 확인하지 못했다.
9. **사례 수와 캡처:** 요청 사례 수를 1~30개로 받고 성공과 실패 모두 화면을 남긴다.

이 순서의 이유는 각 단계에서 입력과 출력이 실제로 맞는지 확인한 뒤 다음 기능을 연결하기 위해서다.

## 5. 현재 확인한 결과의 의미

- 2026-10-26 실제 모델이 데모 주문 폼용 계획 20개를 생성했고, 정책 검색과 화면 확인 도구를 호출했다. 실행 ID는 `4c0042b2-e714-4869-be6d-8876a5c9909d`다.
- 이 계획을 Playwright로 실행한 결과 20/20 통과했고 PNG 20장이 저장됐다.
- 별도의 고정 계획 20개 통과 결과와 실제 모델 생성 결과를 구분한다. 두 결과 모두 데모 화면과 현재 정책에 대한 검증이며, 다른 사이트에서 같은 품질이 나온다는 뜻은 아니다.
- 자동 검증은 구조, 대상, 근거 ID, 일부 문구를 확인한다. 모든 기대값이 정책 의미와 맞는지는 사람이 검토해야 한다.
