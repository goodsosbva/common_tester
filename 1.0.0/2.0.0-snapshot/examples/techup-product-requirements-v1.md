# 부품 스토어 QA: 제품 기획서 및 요구사항 정의서 v1.0.0

## 1. 제품 목적

이 문서는 로컬 테스트 앱 `techup-demo.html`의 제품 기획과 요구사항을 한곳에 정의한다. Common Tester는 이 문서를 등록해 요구사항별 브라우저 테스트를 만든다. 상품 구매 서비스 전체를 복제하는 문서가 아니다.

공개 [Tech-Up 프로젝트 기획안](https://docs.google.com/document/d/16gP1yR5g0CdxHhqj8PXJoByyoDGGJnpJ/edit), [요구사항 정의서](https://docs.google.com/spreadsheets/d/1lb-SckwF90w3tpbJPMl18hdyDSESCkCRWy9koUEmFbI/edit), [기능 설명](https://github.com/beyond-sw-camp/be12-fin-404Found-Tech-Up-BE)을 참고했다. 원본의 회원가입, 상품 탐색, 장바구니, 쿠폰, 주문, 환불, 관리자 상품 등록 흐름을 선택했다. 아래의 구체적인 값과 오류 문구는 테스트 재현을 위해 새로 정한 규칙이며 원본 팀의 정책이라고 주장하지 않는다.

## 2. 화면과 실행 범위

- 회원가입: 이메일, 닉네임, 비밀번호, 이메일 인증 완료 상태를 입력한다.
- 상품 검색: 상품명, 카테고리, 최대 가격, 가격 정렬을 선택한다.
- 장바구니와 주문: 상품과 수량을 담고 쿠폰을 적용한 뒤 결제한다.
- 관리자 작업: 테스트용 권한을 선택하고 상품을 등록하거나 환불을 승인한다.
- 각 영역의 결과는 해당 영역의 상태 문구와 목록에 표시한다. 페이지 이동 없이 모든 입력 요소가 같은 화면에 있다.
- 네트워크 결제, 실제 이메일 발송, 파일 업로드, 영구 저장은 범위 밖이다. 관리자 권한 선택은 UI 검증용 상태이며 실제 서버 인증을 대신하지 않는다.

## 3. 고정 데이터와 테스트 주소

앱 주소는 `http://127.0.0.1:8765/techup-demo.html`이다. 새 브라우저 컨텍스트를 열면 데이터가 초기화된다. 정상 모드는 기본 주소, 정상 이메일을 거부하는 결함 모드는 `?bug=email`, 재고 초과를 허용하는 결함 모드는 `?bug=stock`이다.

기존 계정은 `existing@example.com`, 닉네임은 `기존회원`이다. 초기 상품은 `CPU 기본형` 100000원 재고 3개, `GPU 중급형` 300000원 재고 1개, `RAM 16GB` 50000원 재고 100개, `SSD 1TB` 120000원 재고 2개, `HDD 2TB` 80000원 재고 4개다.

쿠폰은 `WELCOME10` 전체 상품 금액의 10%, `CPU10` CPU 상품 금액의 10%, `EXPIRED10` 만료, `USED10` 사용 완료다. 할인액은 원 단위로 내림한다. 쿠폰은 주문 결제가 완료될 때 사용 완료가 된다. 앱은 브라우저 컨텍스트마다 최근 주문 1건만 보관한다.

## 4. 테스트 생성 기준

- 아래 `정상 A`, `정상 B`, `거부 A`, `거부 B`는 문구 하나에서 기본으로 검토할 네 상황이다. 적용하기 어려운 경우에는 그 사실을 적었다. 네 상황을 모두 실행했다는 뜻은 아니다.
- 유효한 조건에서 성공하면 TP, 유효한 조건에서 실패하면 FN이다. 거부 조건에서 성공하면 FP, 거부 조건에서 실패하면 TN이다. TP, FN, FP, TN은 실제 실행 결과의 분류이며 계획 단계에서 네 결과를 억지로 만들어서는 안 된다.
- 성공은 정확한 상태 문구와 데이터 변경으로 판정한다. 거부는 정확한 오류 문구와 데이터가 변경되지 않았는지로 판정한다.
- 검색처럼 실패가 아닌 `0개 결과`는 정상 결과로 판정한다. 존재하지 않는 제품을 오류로 꾸미지 않는다.
- Common Tester는 한 번에 관련 문단 최대 5개만 읽는다. 검사 목적에 아래 요구사항 ID와 기능명을 넣고 영역별로 여러 번 실행한다.

## 5. 회원가입 요구사항

**MEM-01 이메일 형식.** 이메일은 필수이며 공백 없이 `이름@도메인.확장자` 형식이어야 한다. 정상 A `new@example.com`, 정상 B `a.b@example.co.kr`은 다른 필드가 유효하면 `가입되었습니다.`가 나온다. 거부 A 빈 값, 거부 B `broken-email`은 `올바른 이메일을 입력해 주세요.`가 나오고 계정이 추가되지 않는다. 입력: `이메일`. 결과: `#member-status`.

**MEM-02 이메일 중복.** 이메일은 앞뒤 공백을 제거하고 소문자로 비교한다. 정상 A `fresh@example.com`, 정상 B `FRESH2@EXAMPLE.COM`은 처음 사용하면 가입된다. 거부 A `existing@example.com`, 거부 B 같은 컨텍스트에서 방금 가입한 이메일을 다시 제출하면 `이미 가입된 이메일입니다.`가 나온다. 입력: `이메일`. 결과: `#member-status`.

**MEM-03 닉네임 길이.** 닉네임은 앞뒤 공백을 제외한 2~12자다. 정상 A 2자, 정상 B 12자는 가입된다. 거부 A 1자, 거부 B 13자는 `닉네임은 2~12자여야 합니다.`가 나온다. 나머지 필드는 유효하게 입력한다. 입력: `닉네임`. 결과: `#member-status`.

**MEM-04 닉네임 중복.** 같은 닉네임을 다시 사용할 수 없다. 정상 A `새회원`, 정상 B `다른회원`은 각각 새 이메일로 가입된다. 거부 A `기존회원`, 거부 B 같은 컨텍스트에서 이미 가입한 닉네임은 `이미 사용 중인 닉네임입니다.`가 나온다. 입력: `닉네임`. 결과: `#member-status`.

**MEM-05 비밀번호.** 비밀번호는 영문과 숫자를 모두 포함하고 길이는 8~20자다. 정상 A `Abcd1234`, 정상 B `Abcdef12345678901234`는 가입된다. 거부 A `Abc1234`처럼 7자, 거부 B `abcdefgh`처럼 숫자가 없는 값은 `비밀번호는 영문과 숫자를 포함한 8~20자여야 합니다.`가 나온다. 입력: `비밀번호`. 결과: `#member-status`.

**MEM-06 이메일 인증.** 이메일 인증 완료 체크가 있어야 가입된다. 정상 A 처음부터 체크, 정상 B 체크를 해제했다가 다시 체크하면 가입된다. 거부 A 미체크, 거부 B 체크한 뒤 다시 해제하면 `이메일 인증을 완료해 주세요.`가 나온다. 다른 필드는 유효해야 한다. 입력: `이메일 인증 완료`. 결과: `#member-status`.

## 6. 상품 검색 요구사항

**CAT-01 상품명 검색.** 상품명은 대소문자를 구분하지 않는 부분 일치 검색이다. 빈 검색어는 모든 상품을 보여준다. 확인 A `RAM`은 `RAM 16GB` 1개, 확인 B `ram`도 같은 1개, 확인 C `없는상품`은 `검색 결과: 0개`, 확인 D 빈 값은 `검색 결과: 5개`다. 결과: `#search-status`, `#product-list`. 검색 결과 0개는 오류가 아니다.

**CAT-02 카테고리와 가격 결합.** 선택한 카테고리, 상품명, 최대 가격은 모두 동시에 적용된다. 확인 A `CPU`는 1개, 확인 B 최대 가격 `50000`은 RAM 1개, 확인 C `CPU`와 최대 가격 `99999`는 0개, 확인 D `CPU`와 최대 가격 `100000`은 1개다. 최대 가격은 포함 경계다. 결과: `#search-status`, `#product-list`.

**CAT-03 최대 가격 형식.** 최대 가격은 비워두거나 0 이상의 정수로 입력한다. 정상 A 빈 값, 정상 B `50000`은 검색 결과가 표시된다. 거부 A `-1`, 거부 B `1.5`는 `최대 가격은 0 이상의 정수여야 합니다.`가 나오고 기존 검색 결과를 변경하지 않는다. 입력: `최대 가격 (원)`. 결과: `#search-status`.

**CAT-04 가격 정렬.** `낮은 가격순`은 가격 오름차순, `높은 가격순`은 내림차순이다. 확인 A 전체 오름차순 첫 상품은 `RAM 16GB`, 확인 B 전체 내림차순 첫 상품은 `GPU 중급형`, 확인 C `CPU` 필터 후 정렬해도 CPU만 보이고, 확인 D 기본순은 초기 등록 순서를 유지한다. 결과: `#product-list`. 정렬에는 거부 입력이 없다.

## 7. 장바구니 요구사항

**CRT-01 수량 형식.** 한 번에 담는 수량은 1~99의 정수다. 정상 A RAM 1개, 정상 B RAM 99개는 `장바구니에 담았습니다.`가 나온다. 거부 A 0개, 거부 B `1.5`개는 `수량은 1~99의 정수여야 합니다.`가 나오고 장바구니가 바뀌지 않는다. 입력: `상품 선택`, `담을 수량`. 결과: `#cart-status`, `#cart-summary`.

**CRT-02 재고 제한.** 현재 장바구니 수량과 새로 담는 수량의 합이 상품 재고를 넘을 수 없다. 정상 A CPU 3개, 정상 B GPU 1개는 담긴다. 거부 A CPU 4개, 거부 B GPU 2개는 `재고가 부족합니다.`가 나온다. 수량 형식은 유효하게 입력한다. 결과: `#cart-status`, `#cart-summary`.

**CRT-03 같은 상품 합산.** 같은 상품을 다시 담으면 새 행을 만들지 않고 수량을 합친다. 정상 A CPU 1개 다음 2개, 정상 B CPU 2개 다음 1개는 `장바구니: 1종 / 총 3개`가 된다. 거부 A CPU 2개 다음 2개, 거부 B CPU 3개 다음 1개는 재고 부족으로 막히고 기존 수량을 유지한다. 결과: `#cart-status`, `#cart-summary`.

## 8. 쿠폰 요구사항

**CPN-01 쿠폰 상태.** 장바구니에 상품이 있을 때 `WELCOME10`과 적용 대상이 있는 `CPU10`은 사용 가능하다. 정상 A CPU를 담고 `WELCOME10`, 정상 B CPU를 담고 `CPU10`은 `쿠폰이 적용되었습니다.`가 나온다. 거부 A `EXPIRED10`은 `만료된 쿠폰입니다.`, 거부 B `USED10`은 `이미 사용한 쿠폰입니다.`가 나온다. 결과: `#coupon-status`.

**CPN-02 쿠폰 적용 범위.** `CPU10`은 CPU 상품 금액에만 10% 할인을 적용한다. 정상 A CPU 기본형 1개는 할인 10000원, 정상 B CPU 1개와 RAM 1개도 할인 10000원이다. 거부 A RAM만 담고 `CPU10`은 `이 쿠폰은 CPU 상품에만 적용됩니다.`, 거부 B 장바구니가 비어 있으면 `장바구니가 비어 있습니다.`가 나온다. 결과: `#coupon-status`.

**CPN-03 쿠폰 코드와 재사용.** 쿠폰 코드는 대소문자를 구분하지 않는다. 정상 A `welcome10`, 정상 B `CPU10`을 처음 적용하면 할인 문구가 나온다. 거부 A `UNKNOWN10`은 `존재하지 않는 쿠폰입니다.`, 거부 B `WELCOME10`으로 결제한 뒤 다시 그 쿠폰을 적용하면 `이미 사용한 쿠폰입니다.`가 나온다. 거부 시 이전에 적용된 쿠폰은 바뀌지 않는다. 결과: `#coupon-status`.

## 9. 주문과 환불 요구사항

**ORD-01 결제.** 장바구니가 비어 있지 않으면 상품 금액에서 적용된 쿠폰 할인액을 빼고 결제한다. 정상 A CPU 1개는 100000원, 정상 B CPU 1개에 `WELCOME10`을 적용하면 90000원이다. 거부 A 빈 장바구니에서 결제하면 `장바구니가 비어 있습니다.`가 나오고 주문이 생기지 않는다. 성공 시 `최근 주문: PAID`가 표시되고 장바구니가 비워진다. 결과: `#order-status`, `#order-summary`.

**ORD-02 환불 요청.** 최근 주문이 `PAID`일 때만 환불을 요청할 수 있다. 정상 A 결제 직후 요청하면 `환불을 요청했습니다.`와 `REQUESTED_REFUND`가 나온다. 거부 A 주문이 없을 때, 거부 B 이미 요청한 주문에서 다시 누를 때는 `환불 요청 가능한 결제 주문이 없습니다.`가 나온다. 결과: `#order-status`, `#order-summary`.

**ORD-03 환불 승인.** `REQUESTED_REFUND` 주문은 관리자만 승인한다. 정상 A 관리자 권한에서 요청된 주문을 승인하면 `환불이 완료되었습니다.`와 `CANCELED`가 나온다. 거부 A 일반 회원이 승인하면 `관리자만 환불 승인할 수 있습니다.`, 거부 B 관리자라도 환불 요청 전 `PAID` 주문이면 `환불 요청 상태가 아닙니다.`가 나온다. 결과: `#refund-status`, `#order-summary`.

## 10. 관리자 상품 등록 요구사항

**ADM-01 상품 등록 권한.** 상품 등록은 `현재 권한`이 관리자인 경우에만 가능하다. 정상 A 관리자가 CPU 상품 등록, 정상 B 관리자가 RAM 상품 등록을 하면 `상품이 등록되었습니다.`가 나온다. 거부 A 일반 회원의 CPU 등록, 거부 B 일반 회원의 RAM 등록은 `관리자만 상품을 등록할 수 있습니다.`가 나오고 목록이 변하지 않는다. 결과: `#admin-status`, `#product-list`.

**ADM-02 상품명 길이.** 관리자 상품명은 앞뒤 공백을 제외한 2~40자다. 정상 A 2자, 정상 B 40자는 등록된다. 거부 A 1자, 거부 B 41자는 `상품명은 2~40자여야 합니다.`가 나온다. 다른 입력은 유효해야 한다. 결과: `#admin-status`.

**ADM-03 상품 카테고리.** 관리자는 CPU, GPU, RAM, SSD, HDD 중 하나를 선택해야 한다. 정상 A CPU, 정상 B RAM을 선택하면 등록된다. 거부 A `선택` 상태로 제출하면 `상품 카테고리를 선택해 주세요.`가 나온다. 목록에 없는 카테고리는 선택할 수 없으므로 두 번째 거부 사례는 없다. 결과: `#admin-status`.

**ADM-04 상품 가격.** 관리자 등록 가격은 1~1000000원의 정수다. 정상 A 1원, 정상 B 1000000원은 등록된다. 거부 A 0원, 거부 B 1000001원은 `상품 가격은 1~1000000원의 정수여야 합니다.`가 나온다. 결과: `#admin-status`.

**ADM-05 상품 이미지 수.** 테스트 앱에서는 파일 업로드 대신 이미지 개수를 입력한다. 허용 범위는 정수 0~5장이다. 정상 A 0장, 정상 B 5장은 등록된다. 거부 A -1장, 거부 B 6장은 `상품 이미지는 0~5장이어야 합니다.`가 나온다. 실제 이미지 파일 형식과 크기는 이 앱의 검사 대상이 아니다. 결과: `#admin-status`.

## 11. 완료 판정

- 각 요구사항에서 문서에 적힌 입력 조건과 화면 결과가 맞아야 한다.
- 거부 사례는 상태 문구만 확인하지 말고 계정, 장바구니, 상품 목록, 주문 상태가 잘못 바뀌지 않았는지도 확인한다.
- `?bug=email`에서 `new@example.com` 같은 유효한 이메일이 거부되면 FN을 검출해야 한다.
- `?bug=stock`에서 CPU 4개가 장바구니에 담기면 FP를 검출해야 한다.
- 문서 근거 ID, 실행 단계, 기대 문구, 성공 또는 실패 캡처가 Common Tester 결과에 남아야 한다.
