# Common Tester 2.0.0 완성 기획안

이 문서는 제품 기획서와 요구사항 정의서를 근거로 테스트를 만들고, Codex가 Playwright 코드를 작성하며, 실행 결과와 캡처를 확인하는 Common Tester 2.0.0의 기준이다.

## 1. 결정 사항

| 항목 | 결정 |
| --- | --- |
| 기존 버전 | 기존 기능과 코드는 1.0.0에 보관한다. |
| 2.0.0 시작점 | 현재 앱 화면의 구조와 디자인만 참고한다. 화면 뒤의 저장 방식, 문서 처리, 테스트 생성, 실행 로직은 새로 구성한다. |
| 제품 구동 | 개발 중에는 로컬에서 실행한다. Docker와 Kubernetes는 최종 배포 검증 단계에서만 검토한다. |
| 문서 기준 | 제품명과 버전은 디렉터리 경로로 구분한다. 별도 문서 ID와 버전 DB 컬럼은 만들지 않는다. |
| 테스트 명세 생성 | 첫 번째 LLM이 OpenAI API로 근거가 포함된 JSON 명세를 만든다. |
| 코드 생성 | 명세 검증이 끝난 다음 Codex App Server가 Playwright TypeScript 코드를 만든다. |
| 테스트 실행 | Python이 제품을 점검하지 않는다. 생성된 TypeScript 테스트를 Playwright Test와 Node.js로 실행한다. |
| 캡처와 결과 | 성공과 실패 모두 스크린샷을 저장한다. 실패 사례는 별도 목록으로 보여준다. |

## 2. 사용자 흐름

1. 제품과 버전 디렉터리를 선택한다.
2. 해당 디렉터리에 있는 기획서와 요구사항 정의서를 읽는다.
3. 문서를 문단과 조각으로 나누고, 원문과 임베딩을 버전별 SQLite 파일에 저장한다.
4. 사용자가 대상 앱 주소와 검사 범위를 입력한다.
5. RAG가 선택한 버전의 원문 근거를 찾는다.
6. LangGraph가 첫 번째 API LLM을 호출해 Playwright 코드 생성에 필요한 테스트 명세 JSON을 만든다.
7. 명세 출처와 화면 요소를 검증한다. 사용자가 명세를 확인하고 승인한다.
8. 검증된 명세만 Codex App Server에 순서대로 전달한다.
9. Codex가 Playwright TypeScript 테스트 코드를 작성한다.
10. Common Tester가 Playwright Test를 실행한다.
11. 모든 사례의 결과와 스크린샷을 저장하고 실패 목록을 만든다.

## 3. 구성과 담당

| 구성 | 기술 | 역할 |
| --- | --- | --- |
| 화면 | 기존 React 화면 구조를 참고해 재구성 | 문서 버전, 대상 앱, 실행 상태, 명세 승인, 결과를 표시한다. |
| API | FastAPI | 문서 처리, 실행 상태, LangGraph 호출, Codex App Server 연결을 관리한다. |
| 문서 임베딩 | FastEmbed의 다국어 모델 | 문단 의미를 벡터로 만든다. 문서 임베딩은 로컬에서 처리한다. |
| 근거 검색 | SQLite와 Python 코사인 유사도 계산 | 선택한 버전에서 관련 원문 조각을 찾는다. 별도 벡터 서버는 두지 않는다. |
| 명세 생성 | OpenAI API와 LangGraph | 근거를 바탕으로 구조화된 테스트 명세를 만들고 검증한다. |
| 코드 생성 | Codex App Server | 검증된 명세를 받아 TypeScript Playwright 코드를 작성한다. |
| 점검 실행 | Node.js와 Playwright Test | 생성된 TypeScript 테스트를 브라우저에서 실행한다. |
| 결과 보관 | 제품 버전별 SQLite, 실행별 로컬 폴더 | 원문 근거, 명세, 코드, 로그, 캡처를 보관한다. |

Python은 FastAPI, 문서 처리, RAG, LangGraph를 맡는다. 브라우저 테스트 자체와 생성 테스트 코드는 Python으로 작성하지 않는다.

## 4. 제품과 문서 저장 규칙

제품과 버전을 디렉터리로 나타낸다. 디렉터리 경로가 원문과 임베딩을 찾는 기준이다.

| 경로 예시 | 의미 |
| --- | --- |
| documents/techup/v1/ | Tech-Up 제품의 v1 기획 자료 |
| documents/techup/v2/ | Tech-Up 제품의 v2 기획 자료 |
| documents/techup/v1/embeddings.sqlite3 | v1 원문 조각과 임베딩 |
| documents/techup/v1/planning.docx | 사용자가 관리하는 원본 기획서 |
| documents/techup/v1/requirements.md | 사용자가 관리하는 원본 요구사항 |

지원 원문은 DOCX, Markdown, TXT로 제한한다. 원본 파일명과 상대 경로를 보존한다.

같은 버전의 원문을 수정하면 그 버전의 임베딩 파일만 다시 만든다. 새 버전은 새 디렉터리를 만든다. 임베딩 생성 중 오류가 나면 기존 파일을 보존하고, 생성이 끝난 뒤에만 새 SQLite 파일로 교체한다.

## 5. 문단, 조각, 임베딩

### 저장 항목

| 항목 | 저장 이유 |
| --- | --- |
| 상대 파일 경로 | 같은 폴더의 여러 원본 파일을 구분한다. |
| 문단 번호 | 원문에서 근거가 나온 위치를 다시 찾는다. |
| 조각 번호 | 긴 문단을 분리해도 문단 안의 순서를 복원한다. |
| 원문 텍스트 | LLM에 실제 근거를 전달하고 결과 화면에 출처를 표시한다. |
| 임베딩 벡터 | 표현이 달라도 의미가 가까운 문단을 찾는다. |

출처 표기는 파일 경로와 문단/조각 번호를 함께 사용한다. 예: requirements.md, 문단 17, 조각 2.

### 임베딩과 저장 규칙

1. Word 문단 또는 Markdown/TXT의 문단 경계를 읽는다.
2. 긴 문단은 문장 경계에서 나누고 문단 번호와 조각 번호를 붙인다.
3. FastEmbed 다국어 모델로 각 조각의 벡터를 만든다.
4. 원문 텍스트와 벡터를 해당 버전의 SQLite 파일에 함께 넣는다.
5. 벡터에서 원문을 복원하지 않는다. 원문은 원본 파일이 기준이다.

여기서 임베딩 저장은 검색을 위한 데이터 파일이다. 검색엔진, 별도 벡터 DB, 서버형 색인 시스템을 추가하지 않는다. 제품 문서 규모에서는 선택 버전 SQLite의 벡터를 메모리에서 비교하면 충분하다. 문서가 커져 속도가 실제로 문제가 될 때만 SQLite 벡터 확장을 검토한다.

## 6. RAG 검색과 LangGraph

LangGraph는 첫 번째 API LLM이 명세를 완성하고 검증할 때까지만 사용한다. Codex는 LangGraph의 두 번째 LLM 노드가 아니며, 첫 번째 작업이 끝나고 승인된 뒤 별도 App Server 세션으로 시작한다.

### 처리 그래프

| 순서 | 단계 | 처리 |
| --- | --- | --- |
| 1 | load_scope | 선택한 제품/버전 경로와 지원 문서 형식을 확인한다. |
| 2 | load_documents | 선택 폴더 안 원문만 읽는다. |
| 3 | retrieve_evidence | 의미 검색과 요구사항 문구 검색을 함께 하고 출처를 포함해 원문 조각을 모은다. |
| 4 | inspect_page | 대상 로컬 앱에서 접근 가능한 화면 요소와 입력 조건을 수집한다. |
| 5 | generate_spec | OpenAI API LLM이 근거 기반 테스트 명세 JSON을 생성한다. |
| 6 | validate_spec | 출처 존재, 기대 결과, 화면 요소, 요구사항 범위 누락을 검사한다. |
| 7 | request_approval | 사용자가 명세를 확인하고 승인한다. 실패 시 오류와 누락을 표시하고 Codex로 넘기지 않는다. |
| 8 | save_handoff | 승인된 명세, 근거, 대상 주소를 실행 폴더에 저장한다. 여기서 첫 번째 LLM 작업이 끝난다. |

전체 요구사항 검사는 상위 몇 문단만 잘라서 끝내지 않는다. 기능과 요구사항 단위로 근거를 모아 처리하고, 명세의 출처 목록과 처리 대상 요구사항을 대조해 누락을 표시한다.

### 테스트 명세 형식

첫 번째 LLM은 Playwright 코드를 직접 쓰지 않는다. Codex가 코드로 옮기기 쉬운 JSON을 반환한다.

| 필드 | 내용 |
| --- | --- |
| case_id, title | 사례 식별과 사람이 읽을 제목 |
| source_refs | 원본 상대 경로, 문단 번호, 조각 번호 |
| scenario_type | 정상, 거부, 경계, 중복, 권한 등 정책에 맞는 유형 |
| preconditions | 실행 전 필요한 상태 |
| actions | 화면에서 할 입력과 동작 |
| expected | 화면에서 확인할 성공 또는 거부 결과 |
| ui_hints | 관찰된 role, label, test id 등 화면 요소 |
| risk | 놓치기 쉬운 조건과 확인 수준 |

정책에 성공 조건과 거부 조건이 모두 있으면 둘 다 사례로 만든다. 경계값, 중복 입력, 상태 변화 등 문서에 근거가 있는 예외 조건도 추가한다. 사례 수는 고정 숫자로 제한하지 않고 요구사항과 조건 수에 따라 늘린다. 문서에 없는 정책이나 메시지는 만들어내지 않는다.

## 7. TP, FN, FP, TN 분류

사분면은 테스트를 기계적으로 네 개씩 복제하라는 뜻이 아니다. 정상 입력과 거부 대상 입력을 실행하고, 기대 결과와 실제 결과가 맞는지 판단하는 기준이다.

| 입력의 정책상 정답 | 실제 앱 결과 | 분류 | 테스트 판정 |
| --- | --- | --- | --- |
| 성공해야 함 | 성공 | TP | 통과 |
| 성공해야 함 | 거부 | FN | 실패 |
| 거부해야 함 | 성공 | FP | 실패 |
| 거부해야 함 | 거부 | TN | 통과 |

요구사항마다 정상/거부 경로를 확인하고, 결과 요약에 TP, FN, FP, TN 수를 표시한다.

## 8. API LLM에서 Codex로 전달

두 LLM은 한 요청 안에서 동시에 실행하지 않는다.

| 구분 | 첫 번째 LLM | 두 번째 LLM |
| --- | --- | --- |
| 실행 방식 | OpenAI API | Codex App Server |
| 인증 | Common Tester 서버의 OPENAI_API_KEY | PC의 Codex 로그인 |
| 역할 | 문서 근거를 테스트 명세로 구조화하고 검증 | 저장소에 맞는 Playwright TypeScript 코드 작성 |
| 호출 시점 | 실행 시작부터 명세 승인까지 | 첫 번째 작업이 끝나고 사용자가 승인한 뒤 |
| 받는 자료 | 선택 버전 원문과 화면 관찰 결과 | 검증된 테스트 명세와 원문 근거, 실행 대상 |

OpenAI API 키와 Codex 로그인 정보는 서로 대신하지 않는다. API 키를 Codex 코드 작성 작업에 넘기지 않는다. Codex 로그인 토큰도 웹 화면이나 실행 보고서에 노출하지 않는다.

### App Server 연결 절차

Common Tester의 백엔드는 D:\common_tester에서 Codex CLI가 로그인된 상태로 App Server 자식 프로세스를 시작한다. 통신은 표준 입력/출력의 줄 단위 JSON-RPC를 사용한다.

1. codex app-server --listen stdio:// 실행
2. initialize 요청과 initialized 알림을 보낸다.
3. model/list를 조회하고 계정에서 표시되는 모델을 선택한다.
4. thread/start에서 테스트 작업 폴더와 샌드박스 정책을 지정한다.
5. turn/start로 codex-task.md와 승인된 명세를 전달한다.
6. 진행 이벤트를 화면에 표시하고 turn/completed의 상태를 확인한다.
7. completed일 때 생성 코드 경로를 전달받아 Playwright 실행 단계로 이동한다. failed 또는 interrupted면 오류를 기록하고 실행을 막는다.

현재 PC에서 Codex CLI를 0.164.0으로 업데이트하고 D:\common_tester에서 확인했다. model/list의 기본 모델은 gpt-6.1-sol이며, 이 모델에 읽기 전용 테스트 요청을 보내 turn/completed와 응답 본문까지 확인했다. 같은 테스트에서 CLI 0.137.0은 최신 모델 응답의 max 추론 단계를 읽지 못했다. 따라서 실행 전에 Codex CLI 버전과 model/list 응답을 확인한다. 목록에 표시된 다른 모델은 실제 호출을 별도로 완료해야 사용 가능하다고 판정한다.

Codex App Server 공식 설명: https://openai.com/index/unlocking-the-codex-harness/

## 9. Playwright 코드 생성과 실행

Codex는 승인된 명세와 실제 화면 관찰 결과를 바탕으로 TypeScript 테스트 코드를 만든다. 불필요하게 대상 앱 기능을 수정하지 않는다. 테스트 코드와 결과는 Common Tester 실행 폴더에 저장한다.

| 파일 | 용도 |
| --- | --- |
| generated-tests/*.spec.ts | Codex가 작성한 Playwright 테스트 |
| run.json | 실행 ID, 제품/버전 경로, URL, 상태 |
| test-spec.json | 승인된 테스트 명세 |
| evidence.json | 원문 경로, 문단/조각 번호와 근거 발췌 |
| report.json | 사례별 기대값, 실제값, TP/FN/FP/TN, 오류 |
| screenshots/*.png | 성공 또는 실패 각 사례의 캡처 |
| traces/*.zip | 실패 사례 원인 분석용 Playwright trace |

실행은 Node.js와 Playwright Test가 맡는다. Python은 테스트 코드로 앱을 점검하지 않는다.

대상은 사용자가 지정한 로컬 웹앱으로 제한한다. 기본 허용 호스트는 localhost와 127.0.0.1이다. 임의 외부 사이트 호출은 차단한다.

5. 생성된 사례와 근거 위치

7. 실패 사례 원인, 기대/실제 결과, 스크린샷, trace

## 11. 보안과 실패 처리

- 문서 내용과 웹 화면은 신뢰할 수 없는 입력으로 취급한다.
- 프롬프트 인젝션 문구가 있어도 문서/웹 내용으로만 처리하고 명령으로 실행하지 않는다.
- OpenAI API 키는 서버에서만 읽고 브라우저, Codex 프롬프트, 로그, 실행 결과에 넣지 않는다.
- Codex 샌드박스 쓰기 범위는 Common Tester 실행 결과 폴더로 한정한다.
- 외부 경로 접근이나 샌드박스 밖 작업은 승인 요청으로 멈춘다.
- 명세 검증 실패, Codex 실패, 테스트 실행 실패를 각각 구분해 화면에 표시한다.
- 한 테스트가 실패해도 나머지 테스트의 실행과 캡처를 계속한다.
- 성공 여부와 무관하게 각 사례 종료 시 스크린샷을 저장한다.

## 12. 구현 단계

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 1.0.0을 보존하고 현재 2.0 화면을 기준으로 신규 구조를 정한다. | 기존 문서 ID와 고정 실행 로직을 새 설계의 기준에서 제외한다. |
| 2 | 제품/버전 디렉터리 선택과 원문 읽기를 만든다. | DOCX, MD, TXT를 폴더 경로로 선택한다. |
| 3 | 문단/조각 번호와 버전별 embeddings.sqlite3 저장을 만든다. | v1 갱신이 v2 데이터에 영향을 주지 않는다. |
| 4 | RAG 검색과 LangGraph 명세 생성/검증을 만든다. | 각 테스트에 원문 근거와 검증 가능한 기대 결과가 있다. |
| 5 | 명세 검토/승인과 실행 자료 저장을 만든다. | 미승인 명세는 Codex에 전달되지 않는다. |
| 6 | Codex App Server 연결과 이벤트 표시를 만든다. | App Server 모델 선택, 세션 생성, 코드 작성 완료/실패를 구분한다. |
| 7 | Playwright TypeScript 생성과 실행을 만든다. | 승인 명세에서 테스트 파일을 만들고 Node에서 실행한다. |
| 8 | 성공/실패 캡처, 실패 목록, TP/FN/FP/TN 리포트를 연결한다. | 모든 사례의 캡처와 실행 근거를 다시 열 수 있다. |
| 9 | Tech-Up 예제의 정상/오류/경계 조건으로 전체 흐름을 확인한다. | 문서 선택부터 실패 리포트까지 로컬에서 반복 재현된다. |

## 13. 완료 기준

- 제품과 버전은 디렉터리 경로로 선택한다. 문서 ID/버전 컬럼 없이 파일 경로와 문단/조각 번호로 근거를 찾는다.
- 원본은 보존하고, 임베딩은 선택 버전에서만 다시 만든다. 검색 결과와 테스트 명세에서 원문 출처를 확인한다.
- 첫 API LLM의 명세가 승인된 뒤에만 Codex가 시작되고, Codex는 Playwright TypeScript 코드를 만든다.
- Node 기반 Playwright Test가 코드를 실행한다. 성공과 실패 모든 사례에 스크린샷을 저장하고 실패 사례를 별도로 표시한다.
- 실행 폴더에서 명세, 근거, 코드, 결과, 캡처를 다시 확인한다. 개발 검증에는 Docker와 Kubernetes를 사용하지 않는다.
